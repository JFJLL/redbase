# RedBase 套餐与积分 V2 数据库迁移安全与数据合规指南

## 1. 历史账户状态四分类 (A/B/C/D)

为彻底解决“历史周期积分升级后被重复迁成永久积分”的缺陷（N1），本系统将数据库中的所有账户划分为严格的四种业务状态：

| 账户分类 | 数据库特征 | 迁移与开账处置策略 | 资金安全性保证 |
| :--- | :--- | :--- | :--- |
| **A 类：完全未开账历史用户** | `users.credits > 0` 且 `credit_lots` 记录数严格为 0。 | 原子创建 1 笔永久 `source_type='legacy'` 批次，写入 `legacy_migration` 流水，标记 `legacy_credits_migrated=1`。 | 历史永久资产 100% 完整继承，仅结转 1 次。 |
| **B 类：合法 V13+ 账本用户** | 已存在 `cycle` / `topup` / 历史 `legacy` 批次，`users.credits` 仅为派生缓存。 | **禁止创建任何新的 legacy 批次**；同事务直接置 `legacy_credits_migrated=1`。 | 彻底杜绝已入账的周期积分（如 400 分）被凭空再发一份永久积分（防止 400→800）。 |
| **C 类：账实不符异常账户** | `users.credits` 与有效未过期批次可用总和存在差额，或缺失流水。 | 迁移器与结算逻辑不擅自清零或猜测平账；自动归入审计清单 (`scripts/audit-and-repair-billing-v2.js`) 供人工核对。 | 杜绝未经核对的静默扣分或平账。 |
| **D 类：受有缺陷旧 V14 影响账户** | 在旧 V14 执行期间被误加了与周期额度相同的永久批次，或 active 订阅被 `MAX(id)` 废弃。 | 通过增量迁移 V15 与专用 dry-run 审计工具输出差异报表与纠错建议，不自动删除已消费批次。 | 保持数据可回溯，避免真实用户余额变负。 |

## 2. 迁移版本升级顺序与防御策略 (V14 防护 & V15 增量)

### 2.1 针对尚未执行 V14 的库（前置防御）
- 移除了 `WHERE id IN (SELECT DISTINCT user_id FROM credit_lots WHERE source_type = 'legacy')` 的狭窄条件。
- 升级逻辑前置检查：凡用户已有任何 `credit_lots` 记录，立即识别为 B 类账本用户，封堵重复结转入口。
- 移除了按 `MAX(id)` 静默将活跃订阅置为 `superseded` 的粗暴语句；对于存在多张活跃订阅的异常数据，仅在订阅确实已到期时安全沉淀，保留冲突审计线索。

### 2.2 针对已经执行 V14 的库（增量修订 V15）
- 追加版本 15：`billing-v2-closeout`。
- 自动补齐任务级预占表 `task_credit_reservations`。
- 自动补齐 `payment_orders.snapshot_json`、`anchor_day`、`audit_reason` 等安全字段。
- 幂等复核所有已开账用户的标记状态，不强行回滚或重写已有的 `schema_migrations` 记录。

## 3. 迁移演练与验证场景覆盖

项目通过 `node scripts/rehearse-billing-migration.js` 固化了 6 大隔离演练场景：
1. **全新数据库冷启动**：验证全部 9 张核心计费表、V14/V15 字段与索引自动建立成功。
2. **改造前旧数据库直接升级**：验证历史 3 账户共 1750 积分一次性结转永久批次，重跑无任何增发。
3. **合法 V13 库增量平滑升级**：验证字段安全追加，无报错、无锁死。
4. **在途预占与异常对账**：验证在途 20 积分锁定下，可用 30 积分计算无误，结算后保持 30 积分。
5. **已付未履约重放恢复**：验证支付事实确立但发券中断的订单，查单或对账时 100% 可恢复履约。
6. **V13 纯 cycle 批次升级 (N1 硬断言)**：验证只有周期 400 积分的账户，升级后总额仍为 400 分、永久为 0 分，周期到期后精准归 0，绝无永久副本残留。
